# Day 62 笔记｜摘要记忆

## 1. 一句话定位

**摘要记忆（summary memory）**：把窗口装不下的旧对话，压成一段更短的文字，继续挂在上下文里。

Day 61 是「裁掉」；今天是「压扁再挂回去」。

## 2. 前端迁移直觉

| 你熟悉的前端 | Agent 摘要记忆 |
|--------------|----------------|
| 长列表虚拟滚动，远处不渲染 | 旧轮不再整段塞进请求 |
| 把长日志折叠成「N 条摘要」 | `summarize(old_turns)` |
| Redux persist 里存精简 snapshot | 滚动 `summary` 字段 |
| 无限 scroll 丢细节换流畅 | 省 token 换细节损失 |
| 关键栏固定 + 列表滚动 | system/摘要钉在前，最近轮在后 |

结论：摘要是**产品策略**，不是模型能力玄学——你决定何时压、压什么、保留几轮原文。

## 3. 三种记忆（本周地图更新）

```text
短记忆（D61）        摘要记忆（今天）      长期向量记忆（D63）
├─ 当场可见窗口       ├─ 旧轮 → 一段 summary  ├─ 跨会话偏好/事实
├─ 裁剪 / pinned      ├─ 仍在当前会话请求里   ├─ embed + 检索召回
└─ 无损保留或丢掉     └─ 有损压缩             └─ 按需注入
```

## 4. 推荐上下文形状

发给模型时通常长这样：

```text
[system] 你是……
[system] [对话摘要]
         - 用户曾说叫小前端
         - 讨论过 Agent Loop / Guard
[user] 最近一问
[assistant] 最近一答
[user] 当前问题
```

练习约定：摘要也用 `role=system`，正文以 `[对话摘要]` 开头，方便测试识别。

## 5. 滚动摘要 vs 每次重摘要

| 策略 | 做法 | 代价 |
|------|------|------|
| 全量重摘要 | 每次把全部历史丢给 summarizer | 更准，更贵，更慢 |
| 滚动合并（今天） | `new = summarize(刚折叠的轮, previous_summary)` | 便宜；误差会累积 |

真实项目常「滚动为主 + 偶发全量重压」。今天只做滚动合并。

## 6. 为什么 summarizer 要可插拔？

```text
练习 / CI：default_summarize（确定性字符串拼接）→ pytest 稳定
本地联调：llm_summarize（调便宜小模型）→ 摘要更像人话
生产：带超时/重试/失败回退（折叠失败就先硬裁）
```

接口保持一致：

```python
def summarize(
    exchanges: Sequence[tuple[str, str]],
    previous_summary: str | None,
) -> str: ...
```

## 7. 和 Day 61 怎么配合？

常见挂法：

```text
history 增长
  → 若轮数 > keep_recent：折叠旧轮进 summary   ← 今天
  → 再对「摘要 + 最近轮」做 token 预算检查     ← Day 61 思路
  → 送给 Agent Loop
```

顺序别反：先摘要再预算，比「先裁光再后悔」更常见。

## 8. 常见坑

| 坑 | 正确做法 |
|----|----------|
| 摘要把关键偏好弄丢 | 重要事实 `pinned` 原文，或写入长期记忆（D63） |
| 摘要消息越积越长 | 限制 summary 长度；或定期全量重压 |
| 折叠半轮（只 user） | 只折叠完整 user+assistant 对 |
| 原地改 exchanges 入参 | 返回新 list / 新 Result |
| 测试里调真 LLM | 用 mock，保证 CI 可重复 |
