# Day 41 笔记｜Chatbot vs Agent

## 1. 今天学什么？

Phase 3 开篇：先把名字说清楚。业界常把「带 LLM 的产品」一律叫 Agent，导致架构选型混乱。

| 类型 | 一句话 | 典型产出 |
|------|--------|----------|
| **Chatbot** | 在对话里生成文本（答疑、改写、陪聊） | 一段话 / 结构化文本 |
| **Agent** | 为达成目标而**行动**：调工具、观察结果、再决策 | 副作用 + 最终答复 |

前端类比：

- Chatbot ≈ 只渲染文案的组件（props in → JSX out）
- Agent ≈ 带副作用的交互循环（点按钮 → 调 API → 根据响应更新状态 → 可能再调）

## 2. 三信号判别法（今日练习会编码）

| 信号 | 含义 | 偏向 |
|------|------|------|
| `needs_tools` | 必须调用外部能力（搜索、日历、代码执行、DB…） | Agent |
| `has_side_effects` | 会改变外部世界（发邮件、改文件、下单…） | Agent |
| `needs_multi_step` | 需要多轮推理或规划 | **单独不够** |

**今日规则（刻意简化，方便落地）：**

```text
if needs_tools OR has_side_effects → agent
else → chatbot
```

`needs_multi_step=True` 但没有工具/副作用时，仍标 **chatbot**（例如 CoT 解数学题、长文改写）。  
真正的 Agent「多步」指的是：**行动 → 观察 → 再行动**，不是脑子里多想几步。

## 3. 对照表（建议你默写一遍）

| 维度 | Chatbot | Agent |
|------|---------|-------|
| 核心能力 | 理解与生成文本 | 规划 + 调用工具 + 根据观察继续 |
| 与外部世界 | 通常只读上下文 / 知识 | 可读写：API、文件、浏览器… |
| 控制流 | 单轮或会话式问答 | Agent Loop（直到完成或达上限） |
| 失败模式 | 胡说、跑题 | 工具失败、死循环、越权副作用 |
| 评测重点 | 回答质量 / 安全 | 任务成功率、步数、成本、审计 |
| 产品形态 | 对话框 | 对话框 + 工具状态 / 确认 / 轨迹 |

## 4. 易混场景

| 场景 | 归类 | 为什么 |
|------|------|--------|
| 客服 FAQ / 角色扮演 | Chatbot | 纯对话，无行动 |
| 文档 RAG 问答（你刚做的 mini-rag） | Chatbot（增强型） | 检索是只读上下文组装，不是行动循环 |
| 「查天气并告诉我要不要带伞」 | Agent | 需要天气工具 |
| 「帮我把 PR 描述改短」 | Chatbot | 文本改写 |
| 「创建 issue 并 @ 负责人」 | Agent | 副作用（写 GitHub） |
| 思维链解方程 | Chatbot | 多步推理 ≠ 调工具 |

> RAG 可以成为 Agent 的一个**工具**；但单独的 RAG 问答产品，按今日定义仍归 Chatbot 一侧。
