# Day 17 笔记｜采样参数实验

## 1. 今天学什么？

同一条 Prompt，换几个采样参数，模型回答可以「稳如复读」也可以「天马行空」。  
今天要建立的直觉：

| 参数 | 粗暴理解 | 常见取值 |
|------|----------|----------|
| `temperature` | 随机性旋钮：越低越保守，越高越发散 | 0～2（很多场景 0～1 够用） |
| `top_p` | 核采样：只在累计概率前 p 的词里抽 | (0, 1]，常用 0.9～1 |
| `max_tokens` | 最长能生成多少（截断） | 按任务设 |

前端类比：

- `temperature=0` ≈ 表单校验后的「确定文案」
- `temperature` 升高 ≈ 文案生成器打开「创意模式」
- `top_p` ≈ 候选下拉框只保留「还算靠谱」的前几项，再从里面抽

## 2. temperature 到底在调什么？

解码时，模型先给词表打分（logits），再变成概率分布，最后**采样**出一个词。

- **低 temperature**：分布更尖 → 高概率词更容易被选中 → 重复、稳定、可预期  
- **高 temperature**：分布更平 → 低概率词也有机会 → 多样、惊喜，也可能胡言

注意：

1. `temperature=0` 在不少实现里接近「贪婪 / 近似确定」，但不保证跨厂商比特级一致  
2. 不是「越高越聪明」；创意写作可以高一点，抽取 JSON / 分类通常偏低  
3. 同一温度多跑几次，高温度的方差通常更大（今天 Demo 用固定文案模拟差异）

## 3. top_p（nucleus sampling）

按概率从高到低累加，只保留总和达到 `top_p` 的最小词集合，再在这个集合里采样。

- `top_p=1`：不额外裁剪候选  
- `top_p=0.9`：丢掉特别离谱的长尾词  

实践建议（先记这一条就够）：

> **不要同时猛拧 temperature 和 top_p。**  
> 先固定一个（常见：调 temperature，top_p 保持默认），做对比实验。

## 4. 今天练习在练什么工程能力？

不是「背参数定义」，而是搭一个可复用的**实验脚手架**：

```text
同一 messages
  → 对 [0.0, 0.7, 1.5] 依次 complete
  → 收集 SamplingRun
  → 算一点廉价指标（长度 / unique_token_ratio / Jaccard 距离）
  → format 成可读报告
```

这些指标很粗糙，但足够让你：

1. 用代码固化实验，而不是用眼睛瞟一眼终端  
2. 以后换 Prompt / 换模型时，能留下可对比的痕迹  
3. 为 Agent 选型参数时有「先测再定」的习惯

## 5. 和 Agent 工程的关系

| 场景 | 更倾向 |
|------|--------|
| 工具参数抽取、JSON、分类 | 低 temperature |
| 头脑风暴、文案、起名 | 中高 temperature |
| 需要可复现的评测 | 尽量低随机性 + 固定 Prompt + 记日志 |

Agent Loop 里常见坑：把「创意温度」用在「要严格 JSON」的步骤上 → 解析失败 → 无意义重试烧钱。

## 6. 今日一句话

> 采样参数是旋钮不是魔法：先固定 Prompt，再扫一排 temperature，用报告说话。
