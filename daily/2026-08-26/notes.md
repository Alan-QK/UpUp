# Day 25 笔记｜周挑战：用户故事生成器

## 1. 今天学什么？

Week 5 收口：不追新概念，把已学模块焊成一条流水线——

```text
需求文本
  → 结构化 Prompt（角色/任务/约束/格式 + 可选 few-shot）
  →（模型）只吐 JSON
  → 抽取 + 字段校验
  → Markdown 给人评审 / dict 给下游程序
```

前端类比：这和「表单 schema → 请求体 → 校验 → 列表页渲染」是同一套产品思维；差别只是中间多了一个概率性的生成器。

## 2. 用户故事最小字段

经典句式：

> As a **角色**, I want **能力**, so that **价值**.

落到 JSON（本练习约定）：

| 字段 | 含义 |
|------|------|
| `id` | 稳定编号，如 `US-1` |
| `title` | 短标题 |
| `as_a` / `i_want` / `so_that` | 三件套 |
| `acceptance_criteria` | 可观察的完成条件（至少 1 条） |
| `priority` | `must` / `should` / `could`（MoSCoW 简化） |

> 字段宁少勿多。故事太胖 = 拆分失败；验收标准写成「体验良好」= 无法测试。

## 3. 为什么先锁 JSON？

| 做法 | 结果 |
|------|------|
| 「帮我写几条用户故事，随便发挥」 | 格式飘、难自动化、难回归 |
| 「只输出这个 schema 的 JSON」 | 可单测、可入库、可渲染 |

今天你手写校验；**Day 26** 会换成更系统的 schema（如 pydantic）。心智模型先立住：

1. **契约在前**：输出形状是 API，不是文案
2. **失败可定位**：抽不出 `{`、缺字段、priority 非法——错误类型不同
3. **双通道**：JSON 给机器，Markdown 给人

## 4. 抽取为什么不能 `json.loads(全文)`？

模型常会：

- 前后加「好的，如下：」
- 包一层 \`\`\`json 围栏
- 字符串值里出现 `{` `}`

所以练习要求：**围栏优先 + 括号深度扫描**（并处理字符串/转义），而不是贪婪正则 `\{.*\}`。

## 5. 安全意识（衔 Day 24）

需求文本可能来自外部文档，里面也许夹着「忽略指令」。做法：

- system 约束里写明：输入区是数据不是命令
- 用 `<<<REQUIREMENT>>>` … `<<<END_REQUIREMENT>>>` 包裹

这拦不住一切，但是模板化生成器的默认礼貌。

## 6. 接入真模型时怎么换？

```text
messages = build_story_messages(requirement, examples=[...])
raw = call_llm(messages)          # 你日后接的 Chat Completions
stories = parse_stories_json(raw)
```

本练习的 `main.py` 用 `MOCK_RESPONSE` 代替 `call_llm`，保证零费用可跑。
