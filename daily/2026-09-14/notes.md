# Day 38 笔记｜拒答与低相关处理

## 1. 今天在路线图里的位置

```text
D36：Retrieve → Augment → Generate
        ↓
D37：答案附带来源 chunk
        ↓
D38：没依据就拒答（今天）
        ↓
D39 评测 · D40 mini-rag 里程碑
```

能检索、能引用，还不完整——**低相关命中时硬答**，才是幻觉的主入口。

## 2. 为什么要拒答？

| 场景 | 硬答后果 | 拒答收益 |
|------|----------|----------|
| 库里没有相关资料 | 模型编造「看起来像」的答案 | 用户知道该查别处 |
| top-1 分数很低 | 答非所问，引用误导 | 明确「资料不足」 |
| top-1 / top-2 几乎同分 | 答到错误文档 | 提示歧义，或要求改写问题 |

一句话：**拒答是产品质量，不是模型偷懒。**

## 3. 前端类比

| 前端 | 今日概念 |
|------|----------|
| 空状态 Empty State | `reason=empty` |
| 请求前 Guard / Feature | `evaluate_retrieval` 门控 |
| 置信度不足禁用提交 | `min_top_score` |
| Toast：「暂无结果」 | `format_refusal` / `display` |

你不会在搜索 API 返回空列表时硬渲染「推荐商品」。RAG 同理：检索没把握，就别进生成。

## 4. 门控放在哪？

```text
用户问题
   → retrieve（拿 contexts + score）
   → evaluate_retrieval（今天）
        ├─ refuse → 直接返回拒答文案（不调 LLM）
        └─ allow  → Augment → Generate →（可选）引用
```

**先判分，再生成**：省钱、省延迟，也避免「模型明明被要求拒答却还是编」。

Prompt 里写「资料不足请说不知道」是**软约束**；分数门槛是**硬门控**。两边都要。

## 5. 两个常用门槛

| 策略 | 含义 | 适合 |
|------|------|------|
| `min_top_score` | top-1 余弦相似度低于阈值 → 拒 | 默认首选 |
| `min_margin` | top-1 − top-2 太小 → 拒（歧义） | 多文档易混淆时 |

阈值**没有万能数**：换 embedding / 语料就要重标定。今天用假向量练习结构；生产用 golden set（D39）调参。

## 6. 产品文案原则

拒答应：

1. **承认不知道**（别假装答了）
2. **给一点原因**（无资料 / 相关度低 / 命中歧义）
3. **给下一步**（换关键词、补充资料、人工客服）

不要只回一个冷冰冰的 `false`。

## 7. 常见误解

| 误解 | 纠正 |
|------|------|
| 有 top-k 命中就能答 | 向量库几乎总会返回 k 条；要看分数 |
| 拒答 = 产品失败 | 可控的「不知道」远好过自信的胡说 |
| 只靠 Prompt 拒答就够 | 模型会违规；门控要在代码里 |

## 8. 今日一句话

> 没有足够依据时，明确说「不知道」——这是 RAG 的质量控制，不是功能缺失。
