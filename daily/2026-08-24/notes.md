# Day 23 笔记｜CoT 与直接回答对比

## 1. 今天学什么？

Day 21–22 解决了「Prompt 怎么写结构、怎么用示例」。  
今天回答另一个常见问题：**同一道题，要不要让模型先想步骤？**

| 策略 | 含义 | 前端类比 |
|------|------|----------|
| Direct（直接回答） | 只输出结论 | API 直接返回 `data`，不要 debug 日志 |
| CoT（Chain-of-Thought） | 先写推理过程，再给结论 | 先打印中间态，再返回结果 |
| 答案锚点 | 约定 `最终答案：xxx` | 约定响应字段名，方便解析 |

> 记忆口诀：**简单题直给，难题拆步；对比靠统一锚点。**

## 2. 为什么要对比，而不是「永远 CoT」？

CoT 的好处：

- 多步算术 / 逻辑题正确率往往更高
- 中间步骤可人工抽检（像看网络瀑布图）
- 出错时更容易定位「哪一步歪了」

CoT 的代价：

- **Token 更多** → 更贵、更慢
- 短任务上可能「想太多」反而胡说
- 若没有统一答案格式，步骤散文会很难自动评测

所以工程上不是「默认开 CoT」，而是：

1. 对任务分类（简单抽取 vs 多步推理）
2. 用小样本做 A/B（今天的练习就是离线版）
3. 需要可解析时，强制 `最终答案：`

## 3. 两套 Prompt 怎么写才公平？

公平对比至少固定这四件事：

| 固定项 | 说明 |
|--------|------|
| 同一题目 | user 内容一致 |
| 同一角色边界 | 都是「解题助手」，不要一边当诗人一边当会计 |
| 同一答案格式 | 都要求最后一行（或明确标记）`最终答案：...` |
| 同一评测器 | `extract_final_answer` + 与期望值比较 |

示意：

```text
【Direct system】
只给出最终结论，不要解释过程。
最后一行必须是：最终答案：<答案>

【CoT system】
先分步骤推理（每步一行，形如 1. ...），再给出结论。
最后一行必须是：最终答案：<答案>
```

## 4. 怎么从模型输出里抽答案？

推荐约定：

```text
1. 先算子女现在年龄：...
2. ...
最终答案：42
```

抽取规则（今日练习实现）：

1. 找**最后一次**出现的 `最终答案：`（兼容模型中途误写）
2. 取该标记后同一行的剩余文本，并 `strip`
3. 若整段没有标记 → `ValueError`（评测失败，而不是猜最后一行）

为什么不「猜最后一行」？  
因为 Direct 偶发会多吐一句客套话；没有锚点时自动评测会漂。

## 5. 对比报告看什么指标？

| 指标 | 含义 |
|------|------|
| `correct` | 抽出的答案是否等于期望（规范化后） |
| `step_count` | 在「最终答案」之前，有多少像步骤的行（`1.` / `1、` 等） |
| `cot_helped` | Direct 错、CoT 对 → 说明这次 CoT「帮上了忙」 |
| `cot_hurt` | Direct 对、CoT 错 → 警惕过度推理 |

前端迁移思考：可以把 `step_count` 和正确性画成一张实验表，像性能对比面板一样，而不是凭感觉说「CoT 更好」。
