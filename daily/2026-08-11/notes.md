# Day 16 笔记｜历史消息裁剪（滑动窗口）

## 1. 为什么必须裁历史？

多轮对话时，每次请求都会带上**整段** `messages`。前端类比：

| 前端 | LLM 会话 |
|------|----------|
| 无限往 `messages` 数组 `push` | prompt 越来越长 |
| 浏览器内存涨、接口变慢 | **撞上下文窗口** / **账单飙升** |
| 虚拟列表只渲染可见项 | 只把「最近有用」的轮次送给模型 |

上下文窗口（context window）= 模型一次能吃下的 token 上限（system + 历史 + 本轮 + 预留给回复）。  
Day 14 你算过钱；今天补工程手段：**主动丢掉旧轮**。

## 2. 滑动窗口：最朴素、也最常用

策略一句话：

> **system 永远保留；user/assistant 历史只留最近 N 轮。**

```text
完整历史:  [U1 A1] [U2 A2] [U3 A3] [U4 A4]
max_turns=2 时发送:

system
U3 A3
U4 A4
+ 本轮 U5
```

特点：

- 实现简单，行为可预期（好测、好讲清楚）
- 代价：模型会「忘记」窗口外的事实（「我叫小前端」若被裁掉，它就不知道了）
- 这不是 bug，是**用遗忘换稳定与成本**

更进阶的策略（本阶段只需要知道名字）：

| 策略 | 思路 | 以后会出现在 |
|------|------|--------------|
| 滑动窗口 | 按轮数/条数硬截 | 今天 |
| Token 预算裁剪 | 从旧到新删到估 token 达标 | Phase 4/5 |
| 摘要压缩 | 把旧轮总结成一条 system/summary | Phase 4 记忆 |
| 向量召回 | 旧对话进记忆库，按需取回 | Phase 2/4 RAG |

## 3. 裁「发送」还是裁「存储」？

两种都合理，今天练习**两边都做**：

1. **发请求前**：`sliding_window(history)` → 控制 prompt 大小  
2. **追加回复后**：再 window 一次 → 本地 list 也不无限涨

前端类比：

- 发送前裁 ≈ 请求 payload 分页  
- 存储也裁 ≈ Redux 里对话 slice 设上限，避免 DevTools 炸

调试产品时你可以分开：UI 仍展示更长历史，但 API 只带窗口——今天为降低心智负担，二者同步。

## 4. 实现要点（对应练习）

1. **按「轮」而不是乱切半条**  
   一对 `user + assistant` = 1 轮。不要留下落单的 `assistant` 当窗口开头。
2. **system 不进 history 数组**  
   与 Day 12 一样：人设单独字段，拼消息时放最前。
3. **`max_turns < 1` 直接 ValueError**  
   窗口为 0 没有工程意义（除非你做「无状态单轮」，那是另一产品形态）。
4. **返回新 list**  
   `sliding_window` 不修改入参；`history()` 返回副本——和 Day 12 同一纪律。

## 5. 和成本、幻觉的关系

- 窗口越小 → 越便宜、越不容易撞上限 → 越容易丢约束/事实  
- 窗口越大 → 越「记得住」→ 越贵，且旧噪声可能干扰新任务  
- Agent 场景常见默认：短窗口 + 重要事实写入 **Memory/Scratchpad**（后面 Phase 学），而不是无限堆 messages
